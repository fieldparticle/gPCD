\section{Lighting Ball}

\subsection{Purpose}

\texttt{LightingBall} is the current lighting bring-up scenario after the
Cathedral and FreeStreamHetero studies were retired.  It keeps the useful
parts of the lighting work in a smaller, more inspectable scene: a stream of
mobile light particles approaches a spherical surface made visible by ordinary
boundary-marker particles.  The sphere gives a known three-dimensional shape
for testing lighting response, surface normals, reflection, and Vulkan export
parity.

\subsection{Configured Sphere}

The scenario uses the configuration item:
\begin{verbatim}
Lighting_ball = {
    x = x_center;
    y = y_center;
    z = z_center;
    radius = radius;
    material_id = material_id;
    wall_flag = wall_flag;
};
\end{verbatim}

The generator samples this sphere and inserts standard boundary particles at
the sampled locations.  These particles remain ordinary boundary markers:
they have boundary \texttt{ptype=2}, occupy cells for broad-phase
locality, and are not mobile physical objects.

The marker particles do not define the collision surface.  When a mobile
source discovers a local sphere marker, the dynamics evaluate the analytic
sphere equation from \texttt{Lighting\_ball}.  The sphere normal is:
\[
    \mathbf n =
    \frac{\mathbf x_{\mathrm{source}}-\mathbf c}
         {\lVert\mathbf x_{\mathrm{source}}-\mathbf c\rVert},
\]
where \(\mathbf c\) is the configured sphere center.  Physical penetration is
computed from the source radius and the signed distance to the analytic sphere
surface.  This keeps the boundary particles in the same role as wall markers:
they make nearby analytic geometry discoverable without becoming the geometry.

\subsection{Python Status}

The Python path is the working reference for the lighting ball.  The
generator \texttt{gbase/GenLightingBall.py} creates the sphere markers and
uses the shared streaming structure for the mobile particle stream.
\texttt{base/ForceDynamics.py} owns the analytic lighting-ball evaluator and
reflects a source from the configured sphere normal when the source is moving
into the surface.

Lighting display now uses the first boundary-space lighting rule.  Photons
remain transport/debug particles.  When a photon contacts the analytic sphere
or another boundary target, the contacted surface region stores a visible
spectral deposit in persistent boundary-space state.  Python remains the
behavioral reference for photon contact and material-source selection; its
current display can use existing boundary markers as a coarse approximation.

The old \texttt{BoundaryLightSample}/\texttt{BoundaryLightState} current and
filtered path remains retired.  Eye position, field of view, diffuse terms,
and specular terms are not active lighting inputs.

\subsection{Vulkan Status}

\texttt{LightingBall\_Vk.inc} is aligned with the Python include at the
configuration level.  It selects the same sphere, cell domain, death bounds,
stream geometry, material properties, radius, and timestep, but writes Vulkan
output names such as \texttt{LightingBall\_Vk.tst}.

The current Vulkan simple export carries the lighting-ball sphere into the
runtime scene.  The generated test file writes \texttt{Lighting\_ball} as a
typed structure, and \texttt{ShaderObj} emits \texttt{sphere.glsl} with the
enabled state, center, radius, material id, and wall flag.  The simple exporter
emits \texttt{ForceDynamicsSimpleLightingBall.glsl}.

The basic particle applications use the clean \texttt{FPM.*} shader family.
\texttt{FPM.*} contains ordinary dynamics and particle diagnostics only.  It
does not include the lighting SSBO or photon lighting behavior.  The lighting
application uses the \texttt{FPML.*} shader family for photon-aware compute
and particle/debug rendering.  The lighting surface itself uses
\texttt{BoundaryLight.vert} and \texttt{BoundaryLight.frag}.  \texttt{FPML.comp}
deposits incidence-weighted spectral color into the OBJ-backed
\texttt{LightingSurfaceVertex.light} resource, and the lighting surface
fragment shader draws ordinary interpolated vertex color.

Vulkan rendering also uses the material-owned color-mode contract.  Material
records contain \texttt{color\_mode} and \texttt{color}.  The generated
\texttt{material.glsl} exposes \texttt{COLOR\_MODE\_COLLISION},
\texttt{COLOR\_MODE\_VELOCITY\_ANGLE}, \texttt{COLOR\_MODE\_SOLID}, and
\texttt{COLOR\_MODE\_LUMENS}.  The shared \texttt{color\_map.glsl} no longer
uses the old named solid color schemes.  In \texttt{LUMENS} mode, uncontacted
photons are transparent unless their photon material has
\texttt{debug\_visible=true}.  Surface illumination comes from boundary-space
state rather than from drawing the moving photon point as the surface color.
The retired eye, diffuse, and specular brightness controls are not part of
the active \texttt{LightingBall} contract.

Photon behavior is carried by runtime \texttt{ptype}, not by the current
\texttt{material\_id}.  During generation a stream whose base material has
\texttt{particle\_type="photon"} emits particles with photon \texttt{ptype}.
At the beginning of each compute frame the photon \texttt{material\_id} is
reset to the base photon material.  When the photon contacts the sphere or a
wall, the collision path sets the photon \texttt{material\_id} to the
contacted surface material for diagnostics and future boundary lighting.
The Python and Vulkan renderers treat \texttt{LUMENS} as debug photon
visibility, so this temporary material change does not become the final
visible surface lighting result.  No separate \texttt{hit\_material\_id}
particle field is part of the active ABI.

The active \texttt{LightingBall\_Py.inc} and
\texttt{LightingBall\_Vk.inc} files intentionally use only the ordinary
viewer controls.  The source cfg exports these fields into the generated
\texttt{.tst} file so Python and Vulkan read the same scene view:
\begin{verbatim}
view_center = [1.5, 1.0, 2.5];
view = [-10.8, -52.4, -1.25];
zoom = 1.25;
view_pan = [-5.0, 4.0];
gl_point_size = 2.0;
\end{verbatim}
The eye-aligned camera keys were removed from the active scene because the
eye no longer participates in lighting.  If that camera mode is needed later,
it should be reintroduced as view/camera configuration rather than as part of
the lighting model.

Vulkan treats the generated \texttt{view} and \texttt{zoom} fields as a
Python-camera mode.  In that mode the Vulkan model matrix remains identity,
the camera orientation is built from the Python view angles, and
\texttt{zoom} maps to the same orthographic half-height convention used by
PyVista \texttt{camera.parallel\_scale}.  The Vulkan application window still
comes from \texttt{mps.cfg}; matching Python framing requires the Vulkan
window aspect to match the Python \texttt{window\_size} aspect.

\subsection{Current Boundary-Space Contract}

\texttt{LightingBall} now proves the first boundary-space path in both Python
and Vulkan:
\begin{itemize}
    \item keep photons as transport/debug particles;
    \item map photon contacts to analytic surface space;
    \item store persistent visible surface-vertex color from the photon
          spectrum, surface spectral response, surface spectral emission, and
          incidence angle;
    \item render the OBJ-backed sphere and wall surfaces from interpolated
          lighting-surface vertex color instead of drawing light only on the
          photon point;
    \item keep \texttt{color\_map.glsl} under exporter ownership so photon
          \texttt{ptype}, temporary photon \texttt{material\_id}, and material
          display behavior cannot drift from the generated Vulkan contract.
\end{itemize}

The current Vulkan lighting resource still stores one
\texttt{BoundaryLightRecord} per spatial cell.  \texttt{ResourceLighting.cpp}
sizes the buffer as \texttt{CellAryW * CellAryH * CellAryL}.  Each record is
initialized with a surface type and surface id so compute can preserve
surface ownership and debug state.  Visible surface lighting now lives in the
OBJ-backed \texttt{LightingSurfaceVertex.light} buffer.

\texttt{ResourceLightingSurface} reads the generated
\texttt{lighting\_surface\_objects} table and loads the configured OBJ files
for the sphere and wall into one combined lighting-surface vertex buffer.  A
surface vertex record contains world position, normal/material metadata,
persistent vertex light, local \(u/v\) metadata, and surface type.  Photon
hits project analytic contacts into the matching surface object and write
weighted splats into nearby OBJ vertices.  The lighting surface fragment path
then draws ordinary interpolated vertex color.

The validated state is that \texttt{LightingBall} in Vulkan runs, shows
OBJ-backed sphere lighting, shows absorbing-wall response, and uses the first
incidence-weighted RGB-band spectral deposit.  The stable visible path is now
\texttt{LightingSurfaceVertex.light}; \texttt{BoundaryLightRecord} remains
useful for ownership/debug state and compatibility while the lighting app
keeps moving toward renderable surface geometry.

The next lighting stages are a diffuse light stream, an absorbing shadow
surface, and a reflective surface.

\subsection{LightingBall Configuration Reference}

The active \texttt{LightingBall.cfg} file is a scene contract, not just a
viewer preset.  The following notes define the fields that are easy to forget
because they affect different parts of Python, Vulkan compute, and Vulkan
rendering.

\subsubsection{Scene And App Selection}

\begin{description}
    \item[\texttt{module\_class = "GenLightingBall.py"}] Selects the
    generator that creates the analytic sphere markers, rectangle wall
    markers, and timed photon stream.
    \item[\texttt{python\_dynamics\_class = "ForceDynamicsLighting"}]
    Selects the Python lighting dynamics layer.  Photon behavior belongs to
    the lighting model, not to the ordinary \texttt{ForceDynamics} path.
    \item[\texttt{photon\_periodic\_recycle\_enabled}] When true, dead photons
    return to their original emitter slots after their lifecycle/death rule
    fires.  This keeps the stream populated without runtime birth admission.
    \item[\texttt{include\_file}] Selects the Python or Vulkan scale include.
    \texttt{LightingBall\_Py.inc} is the smaller Python inspection profile;
    \texttt{LightingBall\_Vk.inc} is the denser Vulkan profile.
\end{description}

\subsubsection{Viewer Fields}

\begin{description}
    \item[\texttt{view\_center}] Physical target point used to frame the
    scene.
    \item[\texttt{view}] Python-style camera orientation exported to the
    generated \texttt{.tst}.  Vulkan uses this when Python-camera mode is
    available.
    \item[\texttt{zoom}] Orthographic scale used for Python/Vulkan visual
    parity.
    \item[\texttt{view\_pan}] Screen-space framing adjustment.  This moves the
    rendered view without changing any physical particle, wall, or cell
    coordinate.
    \item[\texttt{gl\_point\_size}] Particle/debug point size.  This affects
    photon tracer visibility, not surface-light deposit size.
\end{description}

View fields never affect photon transport, collision, cell ownership,
material response, or deposited lighting.

\subsubsection{Domain And Geometry}

\begin{description}
    \item[\texttt{scene\_model}] Authored object-library geometry for
    \texttt{LightingBall}.  The generator derives the compatibility
    \texttt{Lighting\_ball}, \texttt{rectangle\_wall\_segments},
    \texttt{curve\_wall\_segments}, and \texttt{lighting\_surface\_objects}
    data from this block.  Engineering particle simulations may continue to
    author wall-segment geometry directly; the lighting app uses
    \texttt{scene\_model} to keep collision geometry and graphics surfaces
    coordinated.
    \item[\texttt{scene\_model.objects[].roles}] Selects each object's use:
    \texttt{"collision"}, \texttt{"boundary\_markers"}, and/or
    \texttt{"lighting\_surface"}.
    \item[\texttt{rectangle\_u\_segments},
    \texttt{rectangle\_v\_segments}] Optional rectangle-object render mesh
    resolution.  These are positive integers on a
    \texttt{type="rectangle"} scene object.  Missing values default to
    \(\lceil u\_length\rceil\) and \(\lceil v\_length\rceil\).
    \item[\texttt{sphere\_lat\_segments},
    \texttt{sphere\_lon\_segments}] Optional sphere-object render mesh
    resolution.  These are positive integers on a \texttt{type="sphere"}
    scene object.  Missing values default to \(32\) latitude segments and
    \(64\) longitude segments.
    \item[\texttt{Lighting\_ball}] Defines the analytic sphere center,
    radius, material id, and wall flag after \texttt{scene\_model}
    derivation.  Boundary particles are only locality markers; collision and
    surface lighting use the analytic sphere.
    \item[\texttt{rectangle\_wall\_segments}] Defines finite rectangle walls.
    Each wall supplies origin, \(u/v\) axes and extents, inward normal,
    \texttt{wall\_flag}, and \texttt{material\_id}.  Vulkan uses this for
    wall contact and deposit projection.  The visible wall surface comes from
    the OBJ-backed \texttt{lighting\_surface\_objects} path.
    \item[\texttt{cell\_array\_width/height/depth}] Defines the spatial cell
    domain.  Boundary-space lighting allocates one \texttt{BoundaryLightRecord}
    per cell.
    \item[\texttt{death\_bounds}] Defines permanent mobile-particle death
    planes.  Photons can recycle from this death event when periodic recycle
    is enabled.
    \item[\texttt{cell\_occupancy\_list\_size}] Maximum occupancy-list slots
    per cell.  Dense photon streams and boundary markers require this to be
    large enough to avoid overflow.
\end{description}

\subsubsection{Photon Stream}

\begin{description}
    \item[\texttt{particle\_streams.material\_id}] Selects the base material
    for generated photons.  A material whose
    \texttt{particle\_type="photon"} generates photon \texttt{ptype}; photon
    behavior is carried by \texttt{ptype}, not by later color state.
    \item[\texttt{initial\_particle\_velocity}] Initial photon velocity.
    Photon speed is intended to remain fixed; momentum/strength changes are
    represented by relative mass or transport strength, not by changing speed.
    \item[\texttt{radius}] Required per-stream photon radius.  The
    \texttt{LightingBall} stream definitions own their generated particle
    size; a top-level stream radius is no longer accepted when
    \texttt{particle\_streams} is present.
    \item[\texttt{particle\_separation\_distance}] Required per-stream
    surface-to-surface spacing.  The generator uses
    \(2r+\texttt{particle\_separation\_distance}\) as the minimum center
    spacing in every generated direction.
    \item[\texttt{release\_start\_frame}] First frame at which the stream is
    active.
    \item[\texttt{release\_columns}] Number of release waves.  With periodic
    recycle this controls the number of original emitter slots.
    \item[\texttt{particles\_per\_wave}] Number of photons in one wave.  For
    the plane-patch form it must equal
    \(\texttt{span\_u\_count}\times\texttt{span\_v\_count}\).
    \item[\texttt{inlet\_axis}, \texttt{inlet\_value}] Fixed coordinate plane
    for the emitter.
    \item[\texttt{span\_u\_*}, \texttt{span\_v\_*}] The two varying axes,
    extents, and counts across the emitter plane.
\end{description}

\texttt{LightingBall} now derives the wave-to-wave frame gap from physical
stream spacing.  For stream radius \(r\), requested surface separation \(s\),
normal stream speed \(v_n\), and timestep \(\Delta t\),
\[
    \texttt{frames\_per\_wave}
    =
    \left\lceil
      \frac{2r+s}{v_n\Delta t}
    \right\rceil .
\]
This guarantees that adjacent release waves start at least one required
center spacing apart along the travel direction.  The older
\texttt{spacing\_factor} field is retained only as transitional stream
metadata; it is not the active no-overlap rule.

\subsubsection{Material Fields}

The material table has two separate ideas: display/debug color and optical
surface behavior.  These must not be treated as one knob.

\begin{description}
    \item[\texttt{particle\_type}] Generation-time particle class.  Use
    \texttt{"photon"} for the photon material and \texttt{"regular"} for
    ordinary surface materials.
    \item[\texttt{relative\_mass}] Initial particle mass/strength for generated
    particles using this material.  Photon transport strength currently starts
    from this value.  For photons, \texttt{parms.x} is the active
    relative-mass strength and is reduced by surface deposit while velocity
    magnitude remains fixed.
    \item[\texttt{color\_mode}] Particle/debug rendering mode.  Active values
    are \texttt{"COLLISION"}, \texttt{"VELOCITY\_ANGLE"},
    \texttt{"SOLID"}, and \texttt{"LUMENS"}.
    \item[\texttt{color}] Solid/debug base color for the material.  For
    absorbing wall lighting, this is not the brightness control.
    \item[\texttt{debug\_visible}] When true, normally hidden debug particles
    or boundary markers may be drawn.
    \item[\texttt{debug\_color}] Debug draw color used when
    \texttt{debug\_visible=true}.  This does not control deposited light.
    \item[\texttt{spectral\_response}] RGB-band response.  For ordinary
    spectral surface deposit, this multiplies the incoming photon spectrum.
    \item[\texttt{spectral\_emission}] RGB-band visible emission/gain for
    ordinary spectral surface deposit.
    \item[\texttt{photon\_coupling}] Fraction of normal-aligned photon
    momentum/light accepted by the surface.  This is the current brightness
    control for an absorbing shadow wall.
    \item[\texttt{photon\_min\_relative\_mass}] Photon death threshold after a
    surface transfers strength out of the photon.
    \item[\texttt{photon\_surface\_behavior}] Optical behavior selected by
    the contacted surface material.  Current values are described below.
    \item[\texttt{contact\_illumination}] Exported surface update policy for
    contact lighting.  Valid values are \texttt{"max"}, \texttt{"min"},
    \texttt{"current"}, and \texttt{"first"}; these map to generated
    \texttt{CONTACT\_ILLUMINATION\_*} constants for the lighting shaders.
\end{description}

\subsubsection{Photon Surface Behavior}

\begin{description}
    \item[\texttt{"NONE"}] No optical surface action.  Use this for the photon
    material itself; photons should not light or mechanically resolve other
    photons.
    \item[\texttt{"SURFACE\_COLOR"}] Deposit ordinary spectral/material color
    on the contacted surface.  This is the current sphere behavior.
    \item[\texttt{"ABSORB"}] Deposit grayscale light on the contacted wall and
    retire the photon.  The gray value is currently based on
    \[
        \mathrm{gray}
        = \mathrm{normal\_alignment}
          \times \texttt{photon\_coupling}
          \times \mathrm{photon\_relative\_mass}.
    \]
    A head-on photon with \texttt{photon\_coupling=1.0} and full relative mass
    can therefore make the wall white.  Lower \texttt{photon\_coupling} to
    make \texttt{name="shadow\_wall"} darker:
    \begin{verbatim}
    photon_coupling = 0.25;  // darker absorbing wall
    \end{verbatim}
    The wall material \texttt{color}, \texttt{debug\_color},
    \texttt{spectral\_response}, and \texttt{spectral\_emission} do not
    currently lower the absorbing grayscale brightness.
    \item[\texttt{"REFLECT"}] Deposit light, reduce photon strength, and
    reflect the photon when enough strength remains.  This is a planned
    next-stage behavior and should stay separate from the current absorbing
    wall proof.
\end{description}

\subsubsection{Retired Lighting Fields}

Do not add these fields to active \texttt{LightingBall} cfg files:
\begin{verbatim}
boundary_lighting_enabled
boundary_lighting_model
boundary_light_initial_rgb
boundary_light_render_ambient
boundary_light_render_gain
boundary_space_patch_angle
boundary_space_patch_radius
boundary_space_patch_falloff
boundary_light_wall_subdivisions_per_cell
photon_energy
lumens_debug_always_visible
lumens_debug_color
\end{verbatim}

\texttt{boundary\_space\_patch\_*} belonged to the retired proxy-spread model.
The active Vulkan visible surface path is OBJ-backed:
\[
    \textrm{photon contact}
    \rightarrow
    \textrm{surface object span}
    \rightarrow
    \texttt{LightingSurfaceVertex.light}.
\]
\texttt{boundary\_light\_wall\_subdivisions\_per\_cell} was replaced by
per-object rectangle mesh fields in \texttt{scene\_model}.  Photon strength is
now the photon's relative mass, so \texttt{photon\_energy} is retired from
active cfg authoring.

Debug photon visibility belongs to material
\texttt{debug\_visible}/\texttt{debug\_color}, not to the old flat
\texttt{lumens\_*} debug fields.

\subsection{Surface OBJ Export}

Python now generates OBJ-backed render surfaces for \texttt{LightingBall}.
The OBJ files describe renderable surfaces only, not photons or boundary
marker particles.  The generated set is:
\begin{verbatim}
LightingBall_sphere.obj
LightingBall_wall.obj
LightingBall_surfaces.obj
\end{verbatim}

The sphere and wall OBJs are generated from the derived
\texttt{scene\_model}/\texttt{lighting\_surface\_objects} data.  Rectangle
mesh density comes from \texttt{rectangle\_u\_segments} and
\texttt{rectangle\_v\_segments}; sphere mesh density comes from
\texttt{sphere\_lat\_segments} and \texttt{sphere\_lon\_segments}.  The same
OBJ files are loaded by \texttt{ResourceLightingSurface}, so Blender can
inspect the same graphics surface that Vulkan draws.

This export is an inspection tool.  Runtime collision still uses the analytic
sphere and rectangle-wall equations, and the particle/bin data should not be
mixed into the surface OBJ.

\subsection{Current Vulkan Beam Verification}

On 2026-07-28, \texttt{LightingBall\_Vk} captures
\texttt{LightingBall\_Vk\_121.cap} through
\texttt{LightingBall\_Vk\_150.cap} were checked against the generated stream
layout.  The generated photon streams were:
\begin{itemize}
    \item front beam: \(90 \times 90 = 8100\) photons, radius \(0.025\),
          separation \(0.005\), required center spacing \(0.055\), span
          spacing \(0.156706\), \texttt{frames\_per\_wave}=6, travel spacing
          \(0.0566914\);
    \item diffuse back beam: \(80 \times 80 = 6400\) photons, radius
          \(0.025\), separation \(0.005\), required center spacing \(0.055\),
          span spacing \(0.176543\), \texttt{frames\_per\_wave}=6, travel
          spacing \(0.0566914\).
\end{itemize}

The overlap validator reported \(14500\) generated stream particles, no
same-birth overlap, and no cell-array out-of-bounds occupancy.  The capture
files decode as \(14908\) records at the lighting-particle stride of
\(256\) bytes.  At frame 150, unhit front photons were at \(x=5.332242\),
matching the expected \(x=5.332247\), and diffuse-back photons were at
\(x=14.167690\), matching the expected \(x=14.167753\).  Front photons that
had reached the sphere surface were already showing contact/reflection state,
which is expected because the sphere begins at \(x=5\).
