\section{Boundary-Space Lighting}

\subsection{Purpose}

Boundary-space lighting is the active surface-lighting direction for
\texttt{LightingBall}.  Its purpose is to let photons light part of an
analytic or implicit surface without turning the moving photon point into the
visible lighting result.

The current model separates responsibilities:
\begin{itemize}
    \item particles carry motion, identity, and collision/debug state;
    \item materials provide source color and debug visibility settings;
    \item boundary markers make analytic surface regions discoverable;
    \item \texttt{BoundaryLightRecord} stores persistent cell/surface
          ownership and debug color;
    \item \texttt{LightingSurfaceVertex.light} stores visible surface color;
    \item the renderer displays interpolated lighting-surface vertex color.
\end{itemize}

This keeps photons as transport/debug particles while allowing a surface region
to remain lit after contact.

\subsection{Cell-Owned To Surface-Vertex State}

The first Vulkan proxy-kernel implementation stored one lighting record per
boundary particle.  That proved the contact-to-light path, but sparse boundary
markers produced point-like circles, fan-out, and visible gaps.  The next
Vulkan model stored lighting by spatial cell.  That proved surface ownership,
but rectangle-wall shadows were visibly quantized by cell boxes.

The active visible model is now:
\begin{verbatim}
photon hits analytic surface
analytic contact maps to surface space
LightingSurface[vertex_id].light stores visible deposited color
renderer interpolates that color across OBJ triangles
\end{verbatim}

The boundary marker keeps its base material identity and broad-phase locality
role.  The visible light state is separate resource state:
\begin{verbatim}
material_id                      = base surface material
LightingSurface[vertex].light.rgb = persistent visible light
LightingSurface[vertex].light.w   = valid flag
\end{verbatim}

Each cell record also carries surface ownership metadata:
\begin{verbatim}
BoundaryLight[cell_id].normal_material.xyz = surface normal
BoundaryLight[cell_id].normal_material.w   = material_id
BoundaryLight[cell_id].ids.x               = cell_id
BoundaryLight[cell_id].ids.y               = surface_type
BoundaryLight[cell_id].ids.z               = surface_id / wall_flag
\end{verbatim}
Cells that do not contain a known renderable surface use
\texttt{surface\_type=NONE}.  Cells near the configured lighting sphere use
\texttt{SPHERE/LIGHTING\_BALL\_WALL\_FLAG}.  Cells near a finite rectangle
wall use \texttt{RECTANGLE\_WALL/wall\_flag}.  This remains useful for
surface ownership and debug inspection, while the active visible wall and
sphere surfaces render from \texttt{LightingSurfaceVertex.light}.

\subsection{Photon Hit Rule}

The first rule is intentionally simple:
\begin{verbatim}
photon hits surface
surface vertex span = lookup(surface_type, surface_id)
nearby surface vertices receive visible deposited color
\end{verbatim}

The color does not clear every compute frame.  It persists until another photon
updates the same surface vertices.  This is still a color-state rule, not an additive
energy-accumulation rule.

Because the first model sets color instead of adding energy, no atomic add is
required.  If two photons write the same surface vertex in the same compute
dispatch, the first implementation accepts last-writer-wins or current
component-wise maximum behavior.  If later work needs additive light
transport, atomic accumulation can be introduced as a separate, deliberate
feature.

\subsection{Analytic Sphere Surface}

For \texttt{LightingBall}, photon contact is evaluated against the analytic
sphere, not against the marker particles.  When a photon contacts the sphere,
the compute shader writes the cell containing the analytic hit point:
\begin{verbatim}
hitPoint = LIGHTING_BALL_CENTER + contactNormal * LIGHTING_BALL_RADIUS
cell_id = CellAddress(hitPoint)
BoundaryLight[cell_id].rgb_valid = visibleDeposit, valid=true
\end{verbatim}

The lighting sphere render resource uses the existing sphere mesh only as a
canvas.  During \texttt{ResourceLightingSphere::Create}, each unit-sphere
vertex is mapped to the configured world-space sphere and assigned an owning
cell address:
\begin{verbatim}
sphereNormal = normalize(unit sphere vertex)
worldPos = LIGHTING_BALL_CENTER + sphereNormal * LIGHTING_BALL_RADIUS
surfaceCellId = CellAddress(worldPos)
\end{verbatim}

The initial version passed \texttt{surfaceCellId} to the fragment shader as a
flat value.  That made triangle ownership visible.  The active version passes
the fragment world position and computes the owning cell per fragment:
\begin{verbatim}
surfaceCellId = CellAddress(surfaceWorldPos);
BoundaryLightRecord record = BoundaryLight[surfaceCellId];
\end{verbatim}

If the record is valid and belongs to the lighting-ball surface, the fragment
uses the stored color at full alpha.  If it is invalid, the fragment is
discarded.  The fragment shader also samples the current cell and the six
face-neighbor cells, weighting by distance to cell centers.  That removes most
triangle-edge artifacts while preserving the cell-owned model.  A bumpy
low-resolution look is expected when the cell field and sphere mesh are still
coarse.

\subsection{Point-List And Surface Rendering}

The ordinary particle/debug pass still uses:
\begin{verbatim}
inputAssembly.topology = VK_PRIMITIVE_TOPOLOGY_POINT_LIST;
\end{verbatim}

That pass remains useful for photons and particle diagnostics.  It is not the
final surface canvas.  \texttt{ParticleLighting} now also has a
lighting-specific surface pass for \texttt{LightingBall}.  The mesh used by
that pass is render geometry only; collision remains analytic, and the
generated boundary markers remain broad-phase locality records.

The lighting surface pass is parameterized by surface identity.  A sphere draw
passes \texttt{SPHERE/LIGHTING\_BALL\_WALL\_FLAG} to the fragment shader.  A
rectangle wall draw passes \texttt{RECTANGLE\_WALL/wall\_flag}.  The fragment
shader then samples \texttt{BoundaryLightRecord} entries only when their
stored \texttt{surface\_type} and \texttt{surface\_id} match the active pass.
This keeps one shared lighting sampler while allowing multiple analytic or
generated surfaces to share the same cell-owned lighting buffer.

\subsection{Vulkan Implementation}

The Vulkan version uses the existing record name:
\begin{verbatim}
struct BoundaryLightRecord {
    vec4 rgb_valid;
    vec4 normal_material;
    uvec4 ids;
};
\end{verbatim}

The buffer is owned by \texttt{ResourceLighting.cpp}, sized as
\texttt{CellAryW * CellAryH * CellAryL}, and bound at descriptor binding 8
only for the \texttt{ParticleLighting} application.  Basic particle
applications remain on \texttt{FPM.*} and do not see this resource.

\texttt{FPML.comp} is the lighting compute schedule.  The current visible
surface path deposits into \texttt{LightingSurfaceVertex.light} records, with
\texttt{BoundaryLight[cell\_id]} retained as surface ownership and debug
state.  The lighting compute path reads material optical fields from the
generated \texttt{MaterialProperty} table.  In particular,
\texttt{photonCoupling} controls the fraction of normal-aligned photon
strength accepted by a surface, \texttt{photonMinRelativeMass} controls the
remaining-strength death threshold, and \texttt{photonSurfaceBehavior}
selects the photon/surface rule.  These GLSL fields are generated from the
cfg names \texttt{photon\_coupling},
\texttt{photon\_min\_relative\_mass}, and
\texttt{photon\_surface\_behavior}; they must not be hardcoded in
\texttt{FPML.comp}.

\texttt{ResourceLighting.cpp} initializes one record per cell and marks
whether that cell is owned by no surface, the lighting sphere, or a
configured rectangle wall.  Sphere ownership is assigned by testing distance
from the cell center to the configured sphere radius.  Rectangle wall
ownership is assigned by projecting the cell center onto the wall plane,
checking the distance to the plane, and then checking the projected point
against the wall's \(u/v\) extents.

\texttt{BoundaryLight.vert} passes surface coordinates and the active render
surface identity to \texttt{BoundaryLight.frag}.  Sphere and rectangle wall
surfaces now come from \texttt{ResourceLightingSurface}, a lighting-only
resource that reads \texttt{lighting\_surface\_objects}, loads the configured
OBJ files, and fills one combined surface-vertex buffer.  The surface buffer
uses:
\begin{verbatim}
struct LightingSurfaceVertex {
    vec4 pos;          // xyz world position, w surface_id
    vec4 normal_flag;  // xyz normal, w material_id
    vec4 light;        // rgb, valid; compute writes this
    vec4 meta;         // local_u, local_v, vertex_id, surface_type
};
\end{verbatim}
and is bound as both a graphics vertex buffer and compute-visible storage
buffer for the \texttt{ParticleLighting} application.  The wall render path
and the sphere render path both read interpolated vertex light from this
buffer.  \texttt{ShaderObj.cpp} also generates
\texttt{LIGHTING\_SURFACE\_OBJECTS} metadata from
\texttt{lighting\_surface\_objects}; each entry carries
\texttt{surfaceType}, \texttt{surfaceID}, \texttt{materialID},
\texttt{vertexOffset}, and \texttt{vertexCount}.  Rectangle-wall analytic
geometry remains separate and is used only for collision/deposit projection.
Since compute updates lighting surfaces that graphics reads as vertex input,
the \texttt{ParticleLighting} compute-finished wait includes vertex input,
vertex shader, and fragment shader stages.

\subsection{OBJ-Backed Surface Vertex Lighting}

The absorbing rectangle wall exposed a limitation of pure cell-owned render
color: a circular photon stream looked square because the visible result was
snapped to cell boxes.  The active implementation keeps
\texttt{BoundaryLightRecord} as the stable surface ownership/debug deposit,
but writes visible wall and sphere color into the
\texttt{LightingSurfaceVertex.light} field.

For an absorbing wall hit, \texttt{FPML.comp} now:
\begin{enumerate}
    \item computes the grayscale deposited light from incidence,
          \texttt{photon\_coupling}, and current photon relative mass;
    \item projects the hit point into the wall's local \(u/v\) coordinates;
    \item finds nearby vertices inside the matching OBJ-backed wall surface;
    \item writes a small weighted splat into nearby wall mesh vertices; and
    \item retires the photon for \texttt{ABSORB} material behavior.
\end{enumerate}

For a lighting-ball sphere hit, \texttt{FPML.comp} maps the analytic contact
normal to nearby vertices in the OBJ-backed sphere surface and writes
\texttt{LightingSurfaceVertex.light}.  The sphere and wall fragment paths
therefore draw the same kind of interpolated vertex light.  This lets the
surfaces use ordinary triangle interpolation to soften the footprint without
making the moving photon point the final visible lighting result.  Because
the first generated meshes are non-indexed, vertices are duplicated per
triangle; compute deposits write local surface spans rather than one abstract
shared grid vertex.

\subsection{Material Surface Behaviors}

Vulkan material behavior now matches the Python photon-contact model:
\begin{itemize}
    \item \texttt{NONE}: no light deposit and no photon reflection;
    \item \texttt{SURFACE\_COLOR}: deposit the hit surface material color,
          reduce photon mass, and reflect the photon if it survives;
    \item \texttt{ABSORB}: deposit grayscale energy and retire the photon;
    \item \texttt{REFLECT}: deposit the photon's current payload color,
          reduce photon mass, and reflect the photon if it survives.
\end{itemize}

The configuration item is:
\begin{verbatim}
photon_surface_behavior = "SURFACE_COLOR";
\end{verbatim}
and the generated Vulkan material exporter also accepts numeric values for
compatibility.  Active cfg files should use the string names.

\subsection{Python Reference}

Python remains the behavioral reference for photon contact and material color
selection.  Its renderer may still use existing boundary markers as a coarse
visual approximation, but the Vulkan target is OBJ-backed surface-vertex
lighting.  The Python model should not reintroduce the retired
\texttt{BoundaryLightSample}/\texttt{BoundaryLightState} current/filter path or
make the photon point itself the final visible surface lighting.

Python generates debug surface meshes for \texttt{LightingBall}.  The OBJ
files are inspection artifacts and Vulkan lighting-surface input, not runtime
particle data.  They are generated from the same cfg values used for Vulkan:
\begin{itemize}
    \item \texttt{Lighting\_ball} center, radius, material id, and wall flag;
    \item \texttt{rectangle\_wall\_segments} origin, axes, extents, normal,
          wall flag, and material id;
    \item \texttt{boundary\_light\_wall\_subdivisions\_per\_cell}.
\end{itemize}
This gives a direct debugging loop:
\begin{verbatim}
Python cfg -> .tst/.bin -> Vulkan runtime
Python cfg -> .obj      -> Blender inspection
\end{verbatim}
If Blender shows the intended surface mesh but Vulkan does not, the defect is
in Vulkan resource binding, shader layout, or draw order.  If the OBJ is
wrong, the defect is in generation or configuration.

\subsection{Incidence-Weighted Spectral Deposit}

The first spectral step is active on top of the cell-owned path.  Material
configuration now exports:
\begin{verbatim}
spectral_response = [r, g, b];
spectral_emission = [r, g, b];
photon_energy = value;
\end{verbatim}

The generated Vulkan material record exposes this as:
\begin{verbatim}
vec4 spectralResponseEnergy;  // rgb + photon_energy
vec4 spectralEmission;        // rgb + reserved
\end{verbatim}

During photon deposit, \texttt{FPML.comp} computes:
\[
    I =
    \max \left(0, -\hat{\mathbf v}_{p} \cdot \hat{\mathbf n}_{s}\right)
\]
and writes:
\[
    \mathbf C_{\mathrm{visible}} =
    E_p I
    \mathbf S_{\mathrm{photon}}
    \mathbf R_{\mathrm{surface}}
    \mathbf E_{\mathrm{surface}} .
\]

The behavior-specific result is written to
\texttt{LightingSurfaceVertex.light} for visible OBJ-backed surfaces.
\texttt{BoundaryLight[cell\_id].rgb\_valid} may still be updated as
ownership/debug state, but it is no longer the primary visible surface result.
The render state does not need to know how the color was produced.  It only
draws the current persistent visible color for each lighting-surface vertex and
relies on ordinary triangle interpolation between those vertices.

\subsection{Next Lighting Behaviors}

The next work should extend behavior in this order:
\begin{enumerate}
    \item Diffuse light stream: broaden the photon source into a distributed
          direction field so the scene is illuminated by many incident
          directions rather than a single structured beam.
    \item Absorbing and shadow surface: add a material rule that consumes or
          blocks photons, producing unlit cells behind the absorber without
          reflecting the photon onward.
    \item Reflective surface: add a material rule that redirects photons and
          carries reflected spectral energy to later deposits.
\end{enumerate}

These behaviors should extend the current \texttt{BoundaryLightRecord}
\texttt{rgb\_valid} path before introducing additive accumulation, temporal
filtering, or directional specular storage.

\subsection{Decision}

The active Vulkan path is:
\[
    \textrm{photon hit}
    \rightarrow
    \textrm{incidence-weighted spectral deposit}
    \rightarrow
    \textrm{persistent OBJ surface-vertex color}
    \rightarrow
    \textrm{ordinary interpolated surface color}.
\]

This preserves the useful lesson from the earlier surface-cell idea: lighting
must belong to surface space.  The current implementation achieves that without
making the visible boundary particles carry the final surface color.
